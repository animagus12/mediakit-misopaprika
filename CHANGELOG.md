# Changelog

## [Unreleased]

## [1.17.2] - 2026-09-06
### Changed
- **The theme is no longer greyscale.** Every colour token was `oklch(L 0 0)`, zero chroma, so the app had no brand colour at all: only `destructive` and the unused chart tokens carried any hue. It now runs on a warm paprika palette, picking up the name.
  - **`primary` sits at hue 45 and `destructive` at hue 25**, deliberately apart. One means "go" and the other means "this cannot be undone", so they have to stay tellable apart even though both are warm. The button variants reinforce it: primary is solid, destructive is a tint of itself.
  - **Neutrals carry a trace of the same hue** (chroma 0.004 to 0.012) instead of being pure grey, and dark mode is a warm charcoal rather than neutral black. Flat grey next to a warm accent is what read as clinical.
  - **Measured contrast, not assumed.** Light mode: body text 18.85:1, muted 5.83:1, white on the primary button 4.83:1. Dark mode: 17.88:1, 7.73:1, 7.05:1. All pass WCAG AA. Sampled by painting each resolved colour onto a canvas and reading the pixel, because Chrome serialises these as `lab()` and parsing the computed string gives nonsense.
  - **Repainting tokens alone changed almost nothing at first**, which was the real finding: the app used `variant="outline"` 49 times, `ghost` 33 times and `default` once, so `--primary` was referenced essentially nowhere. `/invoices` and `/workspace` now lead with a solid brand-coloured action, matching what `/brands` and `/campaigns` already did. `NewEditorTransactionButton` gained the same `variant` prop `NewBrandButton` already had, so the dashboard can keep passing `outline` and let one action lead that row.
- **Pages use a full-screen monitor.** Six pages capped content at `max-w-screen-lg`, leaving 46% of a 1920px screen empty. The cap now steps 1024 to 1152 at `xl` to 1440 at `2xl`, and the dashboard's nav-card grid gains a fourth column once there is room. Unused width at 1920 drops from 46% to 24%.

### Fixed
- **The control sizes were drawn for a mouse and shipped to phones.** `Button` was 28px tall, `Input` 28px, select triggers 28px: fine at a desk, far under the 44px a thumb needs. Every primitive now carries a `pointer-coarse:` size, so the change is invisible on desktop and applies to any touch device regardless of viewport width. Sub-44px targets on a 390px phone: dashboard 17 to 0, `/workspace` 23 to 2, `/invoices` 25 to 9, `/invoices/new` 34 to 4, `/links-editor` 60 to 6.
  - **Inputs are 16px on touch**, not 14px. iOS Safari zooms the whole page when it focuses a field with type smaller than that, and no amount of layout work undoes it.
  - **Only badges that are actually a button or link get a touch target** (`[button&]`, `[a&]`), since a Badge is usually a static label and blowing all of them up to 44px would wreck every table row.
  - What is left is inline text links inside table cells, which WCAG 2.5.8 exempts and which cannot be 44px without destroying the table. On `/mediakit-generator` the remaining figures are an artifact of measurement: the preview is a transform-scaled A4 sheet, so a 44px control inside it measures 24px on screen. Its mm-accurate print layout depends on that scale.
  - **A left-padding regression, caught and reverted.** Adding `pointer-coarse:px-3` to `Input` put a padding rule inside a media query, which outranked the `pl-7` the three search fields use to clear their inset icon, so the placeholder ran under the magnifier. The primitive now leaves horizontal padding alone so call-site overrides keep working.
- Removed every em dash from the project (742 of them across 126 files) in favour of colons, commas, parentheses and full stops, and replaced the em dash used as an empty-cell placeholder with a hyphen. The two in `AGENTS.md` are left alone: that file is rewritten by `next dev` on each run, so editing it only recreates the change.

### Changed
- **The sidebar is grouped, labelled with icons, and marks where you are.** It was a flat, unlabelled list of nine plain-text links in one "Navigate" group, with nothing distinguishing the page you were on from the eight you weren't, and no icon to find a destination by shape rather than by reading.
  - **The taxonomy lives in `lib/navigation.ts`, not in the sidebar.** A `group` field (`manage` / `create` / `public`) on every `NavEntry` and a `navGroups` list give the sections their order and labels, so the dashboard's nav cards and the sidebar can never disagree about what belongs where: and a new destination joins a section by declaring one, rather than by being added to a second list.
  - **The icons were already there.** Every entry has carried a `LucideIcon` for the dashboard's nav cards; the sidebar simply renders it now, so the same destination looks the same in both places for free.
  - **`/` matches only itself; every other entry owns its nested routes**, so `/invoices/new` and `/invoices/[id]` keep Invoices highlighted rather than leaving the whole menu inert on the pages you reach *from* a menu item.
  - **Collapsed now means an icon rail, not an empty margin** (`collapsible="icon"`). Collapsing the sidebar used to hide navigation entirely(the trigger in the navbar was the only way back) so the state that exists to reclaim width made the app harder to move around. Icons stay, with the built-in hover tooltips naming each one, and a `SidebarRail` gives the edge a drag target.
- **The top bar says where you are, and its controls are real buttons.** It was a sidebar toggle on the left and, on the right, two outlined icon buttons with a bare unstyled `Home` text link wedged between them: nothing named the current page, and the whole right-hand group sat at 28px.
  - **The current section's name sits next to the toggle**, behind a vertical `Separator`. Every page already has an `h1`, but it scrolls away; the bar is `sticky`, so this is what names the page once it has. Resolved through the same `navEntries` the sidebar reads, so the two can't disagree.
  - **`isNavHrefActive` and `dashboardEntry` moved into `lib/navigation.ts`** from the sidebar, and the bar derives its title with a new `currentNavTitle()` built on them. A second copy of "which nav entry owns this route" is exactly the thing that drifts: and nested routes have to resolve (`/invoices/new` reads Invoices), which is not something to reimplement per consumer. The trailing-slash guard keeps `/links-editor` from resolving to Links, and the longest matching href wins so a nested entry added later beats its parent.
  - **All four controls are ghost icon buttons on a 44px touch target** (`pointer-coarse:`, 28px for a mouse), so `Home` stops being a text link with a ~20px hit area and the group reads as one row of controls rather than two outlined boxes flanking some text. The hardcoded `h-[1.2rem] w-[1.2rem]` icon sizes are gone in favour of the button's own sizing.
  - **A bottom border and `env(safe-area-inset-top)`.** The bar is translucent and sticky, so without a border content dissolved into it while scrolling; the inset keeps it clear of the notch, matching what the sidebar now does.
- **Logging out asks first.** It was a single tap, sitting a thumb's width from the theme toggle at 28px, and it ends the session with no undo: the one genuinely destructive control in the shell. It now goes through the same `AlertDialog` pattern the links editor uses for deleting a section. Verified that Cancel closes the dialog and leaves the session intact.

### Fixed
- **The mobile sidebar could not be closed.** Two independent causes, both fixed: `sheet.tsx` sizes a side sheet `data-[side=left]:w-full`, which outranks the `w-(--sidebar-width)` `sidebar.tsx` sets on it by specificity(so on a phone the sheet covered the entire screen, leaving no overlay to tap) and the sidebar hides the sheet's own close button (`[&>button]:hidden`) without offering a replacement. The panel is now pinned to `--sidebar-width` per side and capped at `max-w-[85vw]`, so a strip of overlay is always reachable (48px at 320px wide), **and** the sidebar header carries its own 36px close button on mobile. One fix alone would have done; the overlay is the affordance people reach for by habit, and the X is the one they can see.
- **Three of the nine icons in the collapsed rail had no tooltip.** `SidebarGroupLabel` hides itself in the icon rail with `opacity-0` and `-mt-8`, but an `opacity-0` element still takes pointer events: and the negative margin lifts it over the row *above* it, not its own. So the last item before each group heading (Dashboard, Brands, Edit Media kit) was hovering an invisible label instead of the button, and the rail's only means of naming an icon silently failed on exactly those three. `group-data-[collapsible=icon]:pointer-events-none` on the label is the fix. Verified by hit-testing every row's centre and then driving a real pointer over all nine and reading back the tooltip each one produced.
- **Touch targets follow the pointer, not the viewport width.** Nav rows, the mobile close button and the navbar's sidebar trigger are 44px under `pointer-coarse:` and fall back to the compact 36px/28px desktop sizes otherwise. Width was the wrong signal: a phone in landscape is 844px across, past `md`, so a width-keyed rule handed a thumb the 36px desktop rows. Width describes the layout; `(pointer: coarse)` describes the hand.
- **The panel pads itself out of the notch and the home indicator.** It runs `inset-y-0` for the full height of the viewport, so its first and last rows sat flush against both. Header and footer now add `env(safe-area-inset-top/bottom)` on top of their own padding(the same treatment `links.module.css` already gives the phone-first `/links` page) which resolves to zero on hardware without insets.
- Measured on a real coarse-pointer emulation at 390x844, 320x568 and 844x390 landscape: every one of the 11 interactive elements in the open panel is at least 44px, the nav scrolls rather than clipping when the height is short (320x568 and landscape both), nothing is cut off below the fold, and a tap on the overlay strip dismisses the panel at every size. **The collapsed icon rail is the exception and stays a desktop affordance**: the primitive pins those buttons to 32px with an `!important` rule, and it names them through hover tooltips, which a touch device has no way to trigger, tapping the rail's toggle expands it to the labelled list.

## [1.17.1] - 2026-09-06
### Added
- **`/links` now measures itself: views, unique visitors, and per-link clicks with a click rate, read out in the editor.** The media kit has counted views and visitors for a while, but the links page(the one whose entire job is sending people somewhere) could not say whether any link had ever been tapped. Every decision it invites (what to feature, what to retire, whether a creator code is worth the slot) was being made blind.
  - **Clicks are keyed by `LinkItem.id`**, in a single `links_clicks` hash. That id is already stable across relabelling and reordering(the type says so, and this is the per-link state it was reserved for) so a link keeps its history when it is renamed or dragged, and one `HGETALL` fetches every link's total instead of a read per link.
  - **The card stays a real `<a>` with the real destination, with a `sendBeacon` alongside it** (`components/links/TrackedLink.tsx`), rather than routing clicks through a counting redirect. The URL stays copyable, long-pressable and honest in the status bar, and a link still works with JS disabled or the counter down. The trade is deliberate and worth naming: **the count is a floor, not an exact figure.** `sendBeacon` is what survives the navigation the click is about to start, which a `fetch()` from an unloading document does not.
  - **Only the anchor is a client component.** The card's markup is passed to `TrackedLink` as children and still renders on the server, so tracking adds one small handler to the bundle rather than pulling `LinkCard` across the boundary.
  - **The owner's own traffic is not counted at all.** `isCountableVisit()` in `lib/visitor.ts` gates both writes on the request *not* carrying a valid session, and `/links` skips them for anyone signed in. This was found by measurement, not by review: a browser that only ever loaded `/links-editor` put a view and a unique visitor on the board, because `next/link` prefetches the "View live" link and an **RSC prefetch runs the page's server render exactly like a real visit**. That link is now `prefetch={false}`(there is nothing to gain from prefetching a tab that opens on click) but the gate is the actual fix: it also covers reloading the live page while editing, which inflated the figure one view at a time, and it holds for any route to the page a later edit might add. Verified by requesting `/links` three times with the session cookie (nothing counted) and twice without it (two views, one visitor).
    - **`/mediakit` is gated the same way**, and its leak was the larger of the two: `AppSideBar` renders a nav link to the public page on *every* protected page, and the dashboard renders it again as a nav card, so ordinary dashboard navigation was prefetching(and therefore server-rendering) the page it links to. The figure was counting the owner moving around their own dashboard rather than an audience.
    - **The gate is the fix, not `prefetch={false}`.** With links to both public pages sitting in the sidebar of every protected page, chasing prefetch flags one call site at a time would only have left the next one free to reintroduce the leak; refusing to count a request that carries a valid session holds for every route to the page, including ones a later edit adds.
    - **Neither page's existing history is retroactively separable.** `/mediakit` carries ~140 views and 67 unique visitors accumulated under the old meaning, so that figure stays a blend of owner and audience until real traffic outgrows it. `/links` started from zero, so it is clean from its first request.
  - **The editor preview does not count.** `trackClicks` defaults to false on `LinksPublicView` and only `/links` opts in: the preview renders the same `LinkCard`, and without this the author's own clicks while editing would arrive as traffic. Defaulting to off means a future surface rendering this view has to ask for tracking rather than get it by accident.
  - **The click route validates the id against the published page before writing anything** (`app/api/links/click/route.ts`). `/links` is public so the proxy cannot guard the endpoint, and `incrementLinkClick()` creates whatever hash field it is handed: an unvalidated id from a request body would let anyone grow that key without bound.
  - **`/links` joins `/mediakit` in the proxy's visitor-tracked set, sharing one `mk_visitor_id`.** The cookie identifies a person, not a page, so someone who sees both is one visitor to each rather than two anonymous ids. Each page keeps its own set, so the counts stay separate.
  - New `repositories/linkStats.ts` and `linkStats.server.ts`: the same client-safe-type / server-only-read split the social stats use, so the editor can hold `LinksAnalytics` without pulling a Redis read into its bundle. Derivation lives apart again in `lib/linkStats.ts`: only raw counts are stored, so a rate can never drift out of step with them.
  - **Zero is an honest answer here, not "unknown".** Every counter in `lib/cache.ts` is best-effort(a page render, or the click leaving it, must never fail because KV is unset or unreachable) so an unconfigured store reads as a page nobody has seen yet, which is what the editor should show instead of an error.
  - **An unmeasurable rate reads `-`, not `0%`.** `clickRate` is null when there are no views to divide by; with nothing recorded, zero clicks says nothing about the link. A rate legitimately exceeds 100%(it is per page view, and one visitor may tap several links) which the page-level badge says in its tooltip rather than clamping.
  - **The totals are summed over the links that currently exist**, not over every field in the stored map. A deleted link's history stays in the store (ids are never reused, so it returns intact if the link does) but counting it would put clicks in the total that no row on screen accounts for.
  - Per-link figures sit **outside the collapsible trigger**, so every row shows its clicks and rate while collapsed: comparing links is the point, and that only works without opening each one.
  - Verified end to end against the live KV store: three views from one cookie moved views by three and uniques by one; two clicks landed on the right two links; the editor read back `60% click rate` with `2 · 40%` and `1 · 20%` on the rows that earned them. The test counters were then deleted, so `/links` starts counting from zero.
- **The links editor shows, under each social row, when that platform's figure was last refreshed(and for Instagram, when its access token lapses.** The counts on `/links` come from snapshots a daily cron writes, and nothing in the app said when) the only way to know whether the numbers were current was to read the cron's JSON response by hand, which nobody does until a figure has already gone stale or vanished.
  - New `getSocialStatsSnapshot()` in `repositories/socialStats.server.ts` returns the figures and their write times **from one read**, with `getSocialStats()` now a thin wrapper over it for the public page. A second pass could report a freshness that doesn't belong to the figure on screen, which is worse than reporting none.
  - `SocialStatUpdate`/`SocialStatsFreshness` in `repositories/socialStats.ts` are a **sibling of `SocialStats`, not fields on it**: every value in `SocialStats` is a count, which is exactly what lets `totalFollowers()` sum the object's own values instead of naming each platform. (That filter now tests `typeof count === "number"` rather than `!== null`, so the invariant is enforced rather than assumed.)
  - **`hoursAgo` is computed on the server**, not from a clock read during render: a relative time derived in a component differs between the server pass and hydration. Absolute stamps are formatted `en-GB`/UTC for the same reason.
  - **Absence is the symptom named, not age.** The cached figures carry a 26h TTL, so a stalled job makes the entry vanish rather than drift(a missing snapshot reads "not cached) the daily refresh hasn't run, or it failed", which is the state that actually occurs.
  - New `components/links/editor/SocialRowNotes.tsx`, rendered by `ProfileFields` for every social row and returning null for platforms with no cached figure. It keys off the platform name typed into the row, so it follows a reorder and needs no special-casing in `ProfileFields`.
- **The same readout says whether the Instagram access token is still renewing itself.** The follower figure on `/links` depends on a credential with a 60-day life that renews itself, and nothing in the app said so: the only way to know whether renewal was still happening was to read the cron's JSON response by hand, which nobody does until the number has already gone stale.
  - New `getInstagramTokenStatus()` in `repositories/socialStats.server.ts` and an `InstagramTokenStatus` union in `repositories/socialStats.ts`: the same client-safe-type / server-only-read split the stats themselves use. **It carries no token**, only the expiry and a health verdict: this value crosses into a client component, and a credential has no business in a page's props.
  - **A union, not a nullable record**, because the ways there is nothing to show are not the same thing. `getInstagramToken()` deliberately throws rather than returning null when the store is unreachable or unconfigured(so `"unknown"` (unreadable, as in local dev without KV) stays distinct from `"missing"` (the store answering that nothing is seeded). Collapsing them would put "not connected" in front of someone whose integration is fine. An unparseable expiry is `"unknown"` too, not `"expired"`) a corrupt record shouldn't send anyone to redo an OAuth round trip.
  - **The health threshold is derived from the job's own, not a second copy.** `REFRESH_WHEN_REMAINING_MS` is now exported from `services/instagram.ts`; a token more than ten days inside that 40-day window without having renewed is reported `"overdue"`, since a working cron never sits there. That surfaces a stalled renewal with a month of headroom left, rather than at the point the figure stops updating.
  - In `SocialRowNotes`, `"ok"` reads as muted text saying it renews itself and there is nothing to do; `"overdue"` and `"expired"` take amber and destructive tints(raw palette hues at low opacity, since globals.css has no warning token) and each says the one thing to check. `"unknown"` renders nothing: a content editor is the wrong place to raise an infrastructure alarm.

## [1.17.0] - 2026-09-06
### Added
- **Cron routes fail closed when `CRON_SECRET` is unset.** Both `/api/cron/*` routes compared the incoming header against a template literal built from the env var, so with the variable missing the comparison was against the literal string `“Bearer undefined”`: which any caller can send. A single absent environment variable opened the endpoints instead of closing them; verified by probing both routes with that exact header before and after. Now one `isAuthorizedCron()` in `lib/cron.ts`, shared so the check cannot drift between the two routes, returning false whenever the secret is absent. Production was not exposed(`CRON_SECRET` is set there, which is why the YouTube job has been running) but it was one misconfiguration away.
- **Live Instagram follower count on `/links`, via an `{instagram_followers}` placeholder.** Slots into the mechanism the YouTube count already uses(one entry in `STAT_TOKENS`, one field on `SocialStats`) so the page, the editor preview and the degraded-output rules needed no changes at all.
  - New `services/instagram.ts` against `graph.instagram.com` (Instagram API with Instagram Login). The graph version is **pinned**, not left off the URL: an unversioned call resolves to the oldest version Meta still serves, which is the one most likely to be withdrawn.
  - **The access token lives in Redis, not in the env var.** This is the whole difficulty of the integration and the reason it wasn't done alongside YouTube: a refresh *mints a new token*, and a process cannot rewrite its own environment, so a token held only in `INSTAGRAM_ACCESS_TOKEN` would be frozen at whatever was deployed and die 60 days later. The env var is a **seed**: copied into `instagram_token` on the first run, and never read again while that key exists. Unlike the stats snapshots either side of it, that key deliberately carries **no TTL**: the stats are a cache and may lapse harmlessly, but the token is the only copy of a credential that cannot be re-derived without a fresh OAuth round trip.
  - `getInstagramToken()` is the one accessor in `lib/cache.ts` that is **not** best-effort. Everything else there swallows a Redis failure and returns null, which is right for a figure on a page; here it would be read as "no token stored yet", re-seed from the env var, and overwrite a good refreshed token with a stale one.
  - **A seed token is persisted only once it has been proven.** The first run fetches stats with the env token *before* writing it to Redis: storing it first would persist a mistyped or already-expired token, and since the stored key shadows the env var from then on, correcting `INSTAGRAM_ACCESS_TOKEN` would have had no effect until someone deleted the key by hand.
  - **Renewal is time-based with a wide margin.** `refreshInstagramTokenIfDue()` renews only once a 60-day token has less than 40 days left, so a refresh lands roughly every 20 days and the cron can fail silently for six weeks before anything actually breaks. It also declines to refresh a token younger than 24h, which Meta rejects outright: skipping beats burning the attempt and logging a failure. `now` is a parameter, not a clock read, for the same reason `visibleSections()` takes one.
  - **A separate cron from `refresh-youtube`, deliberately.** Folding both into one route would let a YouTube API outage stop the token renewal, and the two failures are not comparable: a missed stats refresh costs a stale number, a missed token refresh eventually costs a manual OAuth round trip. Within the route, stats are fetched *before* renewal is attempted and a renewal failure is reported rather than thrown: the run still did its main job.
  - **An unconfigured integration answers 200 with `skipped`, not 500.** Until the Meta app setup is finished there is no token, and throwing there fails the job every morning: which teaches you to ignore the alert, exactly in time for it to fire on a real token expiry months later. Genuine failures also `console.error` the message: the response body reaches a caller invoking the route by hand, but the cron's caller is Vercel, which records only the status, so a daily failure was otherwise a bare 500 with no way to tell a bad token from an API outage.
